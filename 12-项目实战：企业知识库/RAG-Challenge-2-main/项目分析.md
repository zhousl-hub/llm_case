## 三、数据流详解

### 阶段1: PDF解析 (`pdf_parsing.py`)

**输入**: `data/test_set/pdf_reports/*.pdf`
**输出**: `debug_data/01_parsed_reports/*.json`

**关键处理**:
- 使用 **Docling** (`DoclingParseV2DocumentBackend`) 进行PDF结构化解析
- 启用OCR (`EasyOcrOptions`) 处理扫描件
- 表格结构识别 (`TableFormerMode.ACCURATE`)
- 支持**多进程并行解析** (`parse_and_export_parallel`)
- 页码序列校正 (`_normalize_page_sequence`): 自动填充缺失页码

**输出JSON结构**:
```json
{
  "metainfo": {
    "sha1_name": "文件哈希",
    "company_name": "公司名称",
    "pages_amount": 120,
    "tables_amount": 45
  },
  "content": [...],  // 每页内容块
  "tables": [...],   // 表格结构化数据
  "pictures": [...]  // 图片信息
}
```

### 阶段2: 表格序列化 (`tables_serialization.py`) — 可选

**输入**: `01_parsed_reports/*.json`
**输出**: 原地修改JSON，增加 `table.serialized` 字段

**核心思想**: 将表格从"二维结构"转为"自包含信息块"

**处理流程**:
1. 提取表格所在页的上下文（前后各最多3个文本块）
2. 将表格HTML + 上下文送入LLM (`gpt-4o-mini`)
3. LLM输出结构化信息块:
   ```json
   {
     "subject_core_entities_list": ["营业收入", "净利润"],
     "relevant_headers_list": ["2022年", "2023年"],
     "information_blocks": [
       {
         "subject_core_entity": "营业收入",
         "information_block": "2022年营业收入为100亿元，单位为人民币..."
       }
     ]
   }
   ```

**为什么重要**: 原始表格的markdown对向量检索不友好，序列化后每行变为独立可检索的文本块。

### 阶段3: 报告规整 (`parsed_reports_merging.py`)

**输入**: `01_parsed_reports/*.json`
**输出**: `02_merged_reports/*.json`

**处理规则**:
- 过滤无用块: `page_footer`, `picture`
- 格式化标题: `page_header` → `# `, `section_header` → `## `
- 表格组渲染: 表头 + markdown表格 + 脚注合并
- 列表组渲染: 有序/无序列表合并
- 文本清洗: 处理Docling遗留命令如 `/zero.pl.tnum` → `0`

### 阶段4: 文本分块 (`text_splitter.py`)

**输入**: `02_merged_reports/*.json`
**输出**: `databases/chunked_reports/*.json`

**分块策略**:
- 使用 `RecursiveCharacterTextSplitter` (LangChain)
- chunk_size: **300 tokens**
- chunk_overlap: **50 tokens**
- 编码器: `tiktoken` (o200k_base / gpt-4o)
- 每页独立分块，保留页码映射

**特殊处理**: 若启用表格序列化，会将序列化表格块插入对应页面分块中。

### 阶段5: 向量库构建 (`ingestion.py`)

**输入**: `chunked_reports/*.json`
**输出**: `databases/vector_dbs/*.faiss`

**双索引体系**:

| 索引类型 | 类 | 算法 | 用途 |
|---------|-----|------|------|
| 向量索引 | `VectorDBIngestor` | FAISS (`IndexFlatIP`) | 语义相似度检索 |
| 稀疏索引 | `BM25Ingestor` | `BM25Okapi` | 关键词检索 |

**嵌入模型**:
- 默认: DashScope `text-embedding-v1`
- 可选: OpenAI `text-embedding-3-large`
- 分批处理: 每批最多25条文本

**设计特点**: 每家公司独立构建一个FAISS索引文件，而非全局索引。这是因为问题通常明确指向特定公司，独立索引可减少噪声。

### 阶段6: 检索与重排 (`retrieval.py` + `reranking.py`)

#### 检索器类型

**1. VectorRetriever** (`retrieval.py:82`)
- 加载所有FAISS索引和对应文档
- 按公司名定位目标索引
- 余弦内积搜索 (IndexFlatIP)
- 支持返回父文档（整页）或chunk

**2. BM25Retriever** (`retrieval.py:16`)
- 基于词频的传统检索
- 加载预构建的 `.pkl` 索引

**3. HybridRetriever** (`retrieval.py:286`) — 最佳配置使用
- 组合向量检索 + LLM重排
- 流程:
  ```
  问题 → 向量检索Top-30 → LLM相关性评分 → 融合排序 → 返回Top-6
  ```

#### LLM重排细节 (`reranking.py`)

**评分融合公式**:
```
combined_score = 0.7 * LLM_relevance_score + 0.3 * vector_distance
```

**两种评分模式**:
- 单条评分: 每个文档独立送入LLM评分
- 批量评分: 每批2-4个文档同时评分（更高效）

**评分标准**: 0-1分，步长0.1
- 0 = 完全无关
- 0.5 = 一般相关
- 1.0 = 完全匹配

### 阶段7: 问题处理与问答 (`questions_processing.py`)

**输入**: `questions.json`
**输出**: `answers_*.json`

**核心流程**:

```python
1. 提取问题中的公司名（正则匹配subset.csv）
2. 判断问题类型：单公司 / 多公司比较
3. 单公司：检索上下文 → LLM生成答案
4. 多公司：拆分为子问题 → 并行处理 → LLM汇总比较
5. 引用页码校验（防止幻觉）
6. 输出结构化答案
```

## 四、Prompt工程分析 (`prompts.py`)

这是项目**最精华的部分**，设计了针对不同答案类型的严格Schema。

### 4.1 问题类型与Schema映射

| 类型 | Schema | 答案格式 | 特殊约束 |
|------|--------|---------|---------|
| `name` | `AnswerWithRAGContextNamePrompt` | `str` / `"N/A"` | 公司名必须与问题一致 |
| `number` | `AnswerWithRAGContextNumberPrompt` | `float` / `int` / `"N/A"` | 单位换算、币种校验、负括号处理 |
| `boolean` | `AnswerWithRAGContextBooleanPrompt` | `bool` | 区分"未提及"和"False" |
| `names` | `AnswerWithRAGContextNamesPrompt` | `List[str]` / `"N/A"` | 职位变动只返回职位名 |
| `comparative` | `ComparativeAnswerPrompt` | `str` / `"N/A"` | 多公司比较最终答案 |

### 4.2 通用输出Schema结构

所有答案类型都包含以下字段:

```json
{
  "step_by_step_analysis": "详细分步推理，至少5步，150字以上",
  "reasoning_summary": "简要总结，约50字",
  "relevant_pages": [58, 79],  // 引用的页码列表
  "final_answer": "最终答案"
}
```

### 4.3 数值型答案的严格约束 (`number` 类型)

```python
# 约束要点（prompts.py:145-196）
1. 明确指标定义，拒绝概念近似的替代指标
2. 上下文指标含义必须与问题完全一致才接受
3. 拒绝需要计算/推导才能得出的答案
4. 币种不符 → N/A
5. 数值带括号表示负数，如 (2,124,837) → -2124837
6. 千为单位需补零，如 4970.5（千美元）→ 4970500
```

### 4.4 比较问题拆分 (`RephrasedQuestionsPrompt`)

```python
# 示例
输入: '2022年哪家公司营收更高，"苹果"还是"微软"？'
输出: {
  "questions": [
    {"company_name": "苹果", "question": "苹果公司2022年营收是多少？"},
    {"company_name": "微软", "question": "微软公司2022年营收是多少？"}
  ]
}
```

## 九、核心设计决策

### 9.1 为什么使用"每公司独立索引"？

在该场景下，问题通常明确指向特定公司（如"万科的营收是多少"）。独立索引的优势:
- **检索精准**: 避免不同公司间相似表述的干扰
- **定位简单**: 通过公司名直接映射到对应索引
- **维护灵活**: 新增/删除公司不影响其他索引

### 9.2 为什么选择"父文档检索"？

年报中的财务数据以表格形式呈现，单个chunk往往只包含表格的一行或部分单元格。返回整页内容确保:
- LLM看到完整表格上下文
- 可以对比不同行/列的数据
- 减少因分块导致的信息断裂

### 9.3 为什么"表格序列化"在最佳配置中被禁用？

`max_nst_o3m`（最佳配置）禁用了表格序列化，原因可能是:
- 表格序列化需要额外调用LLM，成本高、耗时长
- 在竞赛数据中，纯文本+父文档检索已足够回答问题
- 序列化可能引入额外的信息噪声

### 9.4 为什么LLM重排使用 `max_workers=1`？

`reranking.py:178` 中明确设置了 `max_workers=1`:
- DashScope API有QPS限制（500 QPM）
- 重排阶段若并发过高会触发限流
- 串行调用保证稳定性

## 十、优势与局限

### 10.1 核心优势

1. **竞赛级精度**
   - 结构化输出 + 强制思维链有效抑制幻觉
   - 严格的指标匹配规则减少错误答案
   - 引用页码校验机制保证答案可追溯

2. **模块化与可配置性**
   - 7个阶段可独立运行、灵活组合
   - 10+种预置配置覆盖不同场景
   - 支持4种LLM Provider

3. **表格处理深度**
   - Docling精准识别表格结构
   - 可选的LLM序列化增强检索
   - 父文档检索保留完整表格上下文

4. **多公司比较支持**
   - 自动识别问题中的多个公司
   - LLM智能拆分为子问题
   - 并行处理 + 汇总推理

### 10.2 已知局限

1. **代码质量**
   - 无单元测试（README明确说明）
   - 错误处理极简，多处使用裸 `try/except`
   - 存在硬编码路径和魔法数字

2. **API兼容性**
   - IBM WatsonX配置已失效（竞赛专属API）
   - DashScope结构化输出未完全实现（返回字符串而非JSON）

3. **性能瓶颈**
   - Docling在CPU上极慢（单页~8秒）
   - 表格序列化需要大量LLM调用
   - 首次运行需下载~400MB模型

4. **文档一致性**
   - 代码注释中英文混杂
   - 部分变量命名不够规范

## 十二、学习要点总结

### 12.1 可借鉴的设计模式

| 模式 | 实现位置 | 价值 |
|------|---------|------|
| 流水线阶段化 | `pipeline.py` | 每个阶段可独立运行、调试、复用 |
| 配置驱动 | `RunConfig` + `PipelineConfig` | 通过配置切换不同策略组合 |
| 多Provider封装 | `APIProcessor` | 统一接口屏蔽底层差异 |
| 结构化输出 | `prompts.py` | Pydantic Schema强制LLM返回可解析格式 |
| 父文档检索 | `retrieval.py` | 检索chunk但返回完整父文档 |
| 幻觉校验 | `_validate_page_references` | LLM声称的引用必须真实存在 |

### 12.2 适合参考的场景

- 金融/法律文档的智能问答
- 需要高精度数值提取的RAG系统
- 多实体比较类问题处理
