超长上下文：直接“喂”整个文档库
超长上下文技术的核心逻辑非常直观：利用大模型不断扩展的
“记忆容量”，直接将完整的文档库作为上下文输入，从根本
上绕过传统 RAG 架构中的检索与拼接步骤。
传统模式：检索 + 拼接
需要先检索关键片段、再拼接输入，容易割裂内容逻辑，丢失全局信
息。
超长上下文模式：全量“投喂”
打破检索限制，直接将整个知识库塞进模型，让大模型基于完整上下
文进行推理。
支持的海量知识库类型
• 复杂文本：产品说明书、法律合同、财务年报
• 代码与记录：完整代码仓库、数小时的会议记录
工作流简化示意
知识库 ➝ 检索 ➝ 拼接 ➝ 模型 (传统方式)
↓ 优化为 ↓
完整文档库 ➝ 直接输入 ➝ 模型 (超长上下文)
核心价值：从“片段理解”到“全局推理”
让大模型真正“读懂”长文档，回答更精准、逻辑更连贯

大模型长上下文窗口：理论与现实
核心洞察：大模型宣传的上下文窗口长度多为理论最大值，受注意力衰减等影响，实际有效利用率仅约25%。因此，预训练与扩展阶段
的训练策略与数据投入，成为决定长文本处理能力的核心变量。
DeepSeek v3
• 预训练基础：超95%训练(14.8T tokens)
基于4K窗口完成。
• 扩展路径：YaRN两阶段快速扩展，每阶
段仅1000步微调。
→ 4K ➔ 32K ➔ 128K
GLM 5.1
• 预训练基础：超95%数据基于4K窗口完
成预训练。
• 扩展路径：预训练中期设“长窗口适配”
阶段，逐级增加数据量。
→ 4K➔32K(1T) ➔128K(500B) 
➔200K(50B)
Kimi K2.6
• 预训练基础：主力训练(>90%)在4K窗口，
少量在8K窗口。
• 扩展路径：后期增加专门适配阶段，数
据量较少。
• 核心技术：YaRN + MLA (多头注意力) 
双重优化。
结论：主流模型多以4K窗口完成绝大多数预训练，通过YaRN等技术快速扩展。扩展阶段的数据量与技术适配，是拉开长文本
能力差距的关键。

主流大模型预训练窗口对比
核心洞察：训练窗口的演进差异
不同大模型在预训练阶段对长上下文窗口的重视程度差异巨
大。传统模型主要在小窗口（4K/8K）完成绝大部分训练，
依赖后期微调适配长文本。而新一代模型如DeepSeek v4则
打破常规，开创性地将绝大部分训练数据放在超大窗口
（64K/1M）完成，这一架构性的差异可能是其在长文本处
理上表现更优的关键原因。
总结：原生超长窗口训练正成为行业新标杆。这表明，在预训练
阶段“喂饱”长上下文数据，而非仅在微调阶段做适配，是提升
大模型长文本能力的核心路径。
GLM 5.1
• 预训练：>95% 数据在4K窗口完
成。
• 特点：典型传统模式，主要依赖
后期的长窗口适配技术。
Kimi K2.6
• 预训练：主力训练(>90%)在4K，
少量在 8K。
• 特点：与GLM 5.1策略相似，仍
以小窗口训练为基础。

=== PAGE 8 ===

超长上下文：何时能替代 RAG？
超长上下文与 RAG 并非完全对立，而是互补关系。在小体量、单文档场景下，它能提供更连贯的语境；但面对
海量知识，RAG 仍是企业级应用的基石。
适合替代的场景
•小型知识库：当知识库仅几十至几百万Token（如企业制度、
说明书），可直接喂给模型。
•单文档强相关：针对合同分析、财报研读等场景，提供完整语
境避免信息割裂。
•高精度理解：避免Chunk切碎与Embedding失真，更适合处
理表格、跨页引用及代码逻辑。
无法替代的局限
•知识库规模受限：百万级文档、10TB级海量知识无法一次性
塞进上下文窗口。
•成本指数级上升：Token消耗随上下文长度大幅增加，企业规
模化应用难以承受。
•注意力衰减：模型存在“中间遗忘”效应，无法稳定、均匀地
利用超长文本中的所有信息。

Agentic Retrieval的本质：自主的推理过程
在 Agentic Retrieval 范式中，LLM 不再是被动的检索工具，
而是成为了整个流程的主导者，它通过自主决策驱动检索：
搜什么 (What to search)：基于意图理解，将模糊的问题
转化为精准的搜索指令。
何时搜 (When to search)：自主判断是否具备回答问题的
充足背景知识。
下一步搜什么 (Next search)：根据已有信息的缺口，动态
规划后续的搜索路径。
停止或迭代 (Termination/Iteration)：评估信息是否足够
支撑结论，或判断是否存在矛盾，决定继续搜索或终止。
核心转变：
Retrieval becomes Reasoning

核心架构变化：从单次检索到循环推理
传统 RAG 架构：Retrieve 
Once
一个简单的线性流程，缺乏对复杂问题的探索能力：
Query → Retrieve → Generate Answer
“输入即检索，检索即回答”
Agentic Retrieval：Reason-
Retrieve Loop
❶ Reason 推理：LLM深度分析问题，拆解任务并规划下
一步行动。
❷ Retrieve 检索：基于推理结果，精准调用工具执行检索
或计算。
❸ Observe & Decide 观察与决策：评估结果，判断信
息是否足够或是否需要继续探索。
❹ Repeat 循环：在满足终止条件前，持续循环上述过程
以逼近真相。
这是从“一次性”到“持续性”的本质进化



=== PAGE 13 ===

经典实现：ReAct Pattern
几乎所有 Agentic Retrieval 的底层逻辑，都能看到 ReAct 的影子。
它是一种让 LLM 模拟人类思维方式，通过交替进行“推理 
(Reason)”与“行动 (Act)”来逐步拆解、解决复杂问题的核心范
式。
Thought · 思考
基于历史记忆与当前任务，推理分析下一步该执行什么操作
来获取关键信息。
Action · 行动
执行具体的工具调用（如网络搜索、数据库查询或代码运行）
以获取外部反馈。
Observation · 观察
获取并理解行动的结果，将其作为新的上下文输入，为下一
轮思考提供依据。
ܔ 核心循环逻辑
这三步构成一个闭环，不断重复迭代。直到模型通过“观察”
确认已获取足够信息，能够得出可靠结论时，循环才会终止。



=== PAGE 14 ===

ReAct模式企业案例：追踪退款率升高原因
用户问：为什么退款率最近升高？
Step 1: Thought (思考)
LLM 推理假设：退款率升高可能与支付
接口失败、APP新版本上线或近期客服
策略调整有关。
Step 2: Action (行动)
调用日志分析工具进行验证：
`{"tool": "search_logs", "query": "退款
失败 最近7天"}`
Step 3: Observation (观
察)
系统返回结果：
发现第三方支付宝接口的调用失败率异
常上升。
Step 4: 继续思考 (Thought)
基于失败数据，判断需进一步排查：支付系统是否在近期有代码
更新或配置变更？
Step 5: 再次行动 (Action)
调用版本管理工具：
`{"tool": "search_release_notes", "query": "支付系统 最近更
新"}`
✅ 最终，Agent 通过“思考-行动-观察”的自主循环，精准锁定了系统更新导致的支付接口异常根源。

LLM Wiki：从“切碎知识”到“保留结构”
传统RAG最大的痛点是将知识强制“碎片化”，导致上下文断
裂、逻辑关系丢失。LLM Wiki的核心思想是保留知识的原始
结构，为LLM构建一个可阅读、可导航的完整知识空间。
页面化 (Paged Structure)：拒绝盲目的切块，以页面为单
位保持知识的完整语义与逻辑上下文。
双向链接 (Bi-directional Links)：构建实体间的关联网络，
支持LLM像人类一样在知识间自由跳转与探索。
结构化目录 (Hierarchy)：建立层级清晰的目录体系，让海
量的企业知识不再是一盘散沙，结构分明。
智能摘要与索引：自动生成页面摘要与关键索引，大幅提升
LLM的信息定位与快速理解效率。
WHAT IS IT ? 它是什么？
LLM Wiki 是为大模型量身打造的企业级知识体系。它就像
为LLM专门重构的 Confluence 或 Wikipedia，将分散的文
档转化为适合机器阅读、引用与推理的结构化“百科全书”。
核心价值：告别“碎片化失忆”
Structured Knowledge > 
Fragments
让LLM在完整的知识图谱中进行推理

一：页面化 (Page-based Knowledge)
传统RAG的问题
• 切分缺陷：将PDF/文档切成固定大小Chunk，丢失页面
身份。
• 核心问题：无主题边界、语义不完整，无法识别Chunk
归属。
示例：“退款规则”被切分为
Chunk_182 (上半段) + Chunk_183 (下半段)
→ LLM无法识别二者属于同一主题
页面化的实现流程
Step 1: 文档解析
提取标题、段落、表格，保留原始结构。
Step 2: 结构识别
识别Markdown层级，构建父子关系树。
Step 3: 生成Page Object
封装page_id/title/content/summary结构化对象。
从“无边界Chunk”到“结构化Page”的知识重构

四、实体关系 (Entity Relationship)
实体关系抽取是构建知识图谱（LLM Wiki）的核心能力，
其本质是从非结构化文本中，自动识别并抽取出结构化的
“实体”与“关系”，为AI提供可计算的骨架。
ۮ 结构化抽取示例
原文：“张三负责 Apollo 项目。Apollo 项目服务于腾讯。”
结果：(张三, 负责, Apollo)、(Apollo, 客户, 腾讯)
ಝ 为何这是关键？
将信息转化为实体与关系后，才能打破文本孤岛，实现复杂的
多跳推理，让 AI 具备像人一样理解、关联和运用知识的能力。
ट️ 主流实现方法
1.LLM 端到端抽取 (主流):通过精心设计的 Prompt 指令，
直接让大模型输出结构化数据，高效且适配性强。
2.传统 NLP 技术栈:利用依存句法分析、NER等工具，目前
在追求极致效率场景仍有应用，但正逐步被 LLM 方案替代。
ۏ 存储与最终形态
抽取结果通常存入图数据库 (Graph DB)（如 Neo4j），将
海量碎片化信息编织成一张可被高效查询、遍历和推理的知
识图谱 (Knowledge Graph)，为企业构建专属的数字大脑。

五、自动摘要 (Auto Summary)
为什么需要？企业知识通常篇幅过长，大语言模型 (LLM) 难以每次读取全文。因此，需要高效的摘要技术提炼
核心信息，解决长上下文处理难题。
1. Chunk Summary (细粒度摘要)
对长文本的最小语义单元 (Chunk) 进行初步提炼，保留关键事实与数据。
2. Page Summary (页面聚合摘要)
将分散的 Chunk 摘要进行聚合与逻辑整合，生成完整的页面级摘要。
3. Section Summary (全文/章节摘要)
进一步聚合页面摘要，形成文档全貌的宏观摘要，输出关键结论与核心观点。
✨ 高级玩法: Query-aware 
Summary
核心思想：从“为文档生成通用摘要”转变为
“为用户问题动态提取答案”，精准匹配信息需
求。
技术演进：这已接近 Agentic Retrieval 的核心
逻辑，即根据用户意图动态调整信息处理路径，
是 RAG 的重要升级方向。
示例结构: {page:..., summary_short:..., key_points: [...]}

六、自动索引（Auto Indexing）

自动索引的核心思想是为知识建立多样化的访问入口，打破单一向

现代企业级系统普遍采用混合策略以达到最佳效果，其核心组合是：
BM25 (关键词) + Vector (语义) + Graph (关联)

• Vector:理解文本深层语义含
义
• BM25:经典高效的关键词检
索
• Entity:人名/产品名等精准匹
配
• Graph:探索实体关联与多跳
检索
• Hierarchy:支持目录式层级
导航
• Temporal:基于时间维度的过
滤
• Permission:精细化的数据权
限控制
常见技术栈选型
Elasticsearch / OpenSearch：成熟的搜索引擎，支持 BM25

Weaviate / Milvus：专为 AI 构建的向量数据库，提供高性能的

Vespa：支持混合搜索的实时大数据处理引擎，适合低延迟场景。

七、Semantic Navigation（语义导航）
本质：从“召回”到“导航”
不再是简单的 top-k 召回，而是 LLM 像人一样，自主决定下一步该
去哪里探索。
类比：如在维基百科上阅读，不断点击链接，从一个知识点跳转至另

实现：Retrieval as Agent Action
核心流程：reason → retrieve → read → decide next retrieve
常见架构：• ReAct (思考→行动→观察循环) • Tree Search (在知
识图谱上进行BFS/MCTS导航)
本质区别：传统RAG中检索是“系统行为”，而语义导航中检索是
“模型自主行为”。

LLM Wiki 的三层架构：从数据到智能
Karpathy提出的LLM Wiki三层架构，将企业知识系统从简单的“存文档”升级为类似“编译器”的智能系统，实现了从原始数据到结构
化知识的质变，是AI时代构建企业知识库的新思路。
Raw Layer (原始数据
湖)
事实来源 (Source of Truth)：包含文档
(PDF/Word)、代码(Git)、数据库、IM记录
等所有原始、未加工数据。
• 特点：数据混乱、不可控，不适合直接处理。
• 价值：保留原始事实，为回溯提供依据。
Wiki Layer (编译输出
层)
核心知识层：AI“编译”后的结构化知识，
含页面、摘要、实体、双向链接及关系图等。
• 本质：“知识编译器”
• 价值：将原始数据转化为LLM可高效利用的
预编译知识。
Schema Layer (控制
协议)
系统规则层：定义知识宇宙的操作规范，包
括页面模版、实体Schema、命名规范、链
接规则等。
• 价值：统一知识表示，避免实体不统一、命
名混乱，确保系统长期可维护。
核心转变：从 Query-time Intelligence (查询时理解) 转向 Ingest-time Intelligence (摄入时编译)。这一架构的本质，是将“企业
知识库”升级为“AI时代的知识编译系统”。

LLM Wiki：知识的持续演化
核心区别：从“新增”到“重构”
企业知识系统的最大挑战在于应对知识的持续演化。
传统RAG系统将新知识仅作为“素材”进行简单的叠
加，无法更新知识间的深层关联。而LLM Wiki将知识
视为动态系统，在每次更新时进行整体的“编译”与
“重构”，以确保知识网络的准确性与实时性。
传统 RAG (Append-
only)
新文档 → 切分 → 向量化 → 入库
本质：仅新增搜索素材，不会更新摘
要、实体关系等深层结构。知识是孤
立、静态的。
LLM Wiki 
(Recompilation)
新知识 → 解析 → 重构 → 全局更新
本质：类似代码的“增量编译”。新
知识进入后，整个知识空间的实体、
关系和摘要都可能发生连锁变化。
▍ 企业级LLM Wiki的完整知识更新流水线
1. 变更检测(Change Detection) → 2. 文档解析(Document Parsing) → 3. 实体抽取(Entity Extraction) → 4. 关联分析(Link Analysis) → 5. 页面更新
(Page Update) → 6. 摘要重建(Summary Rebuild) → 7. 图谱更新(Graph Update) → 8. 索引刷新(Index Refresh) → 9. 一致性检查(Consistency 
Check)

LLM Wiki：知识更新的触发机制
LLM Wiki 的知识更新不再是人工维护的静态过程，而是由“外部业务事件”与“内部逻辑规则”双轮驱动的

被动触发：内部逻辑驱动

•业务流程产出：项目立项文档、跨部门会议纪要、合规审计报

LLM Wiki的现实挑战
尽管LLM Wiki能有效整合知识，但在构建与维护的过程中，我们面临着以下三大核心挑战：
构建成本高
相比传统RAG“扔文档进去即可”的

Wiki化后，知识之间存在复杂的关系

谱失效，日常维护成本显著高于普通
知识库。
不适合超实时数
据
对于高频变化的股票交易数据、IoT实
时流数据、系统实时日志等超实时数
据场景，直接使用专业的时序数据库
或实时查询工具，在效率上远优于
LLM Wiki。
